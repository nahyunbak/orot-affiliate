## 1. 개요

| 구분               | 내용                                                                                                                                                                                                                                                                                                      |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1) 서비스 요약** | 브랜드 캠페인 집행자가 인스타그램형 피드에서 인플루언서의 게시물과 조건을 검수하고, 승인한 참여자의 지갑에 Maroo 테스트넷 보상을 지급하는 웹앱. 브랜드명은 Influencer와 Chain의 연결을 뜻하며 슬로건은 “브랜드와 인플루언서를 잇다”.                                                                      |
| **2) 문제 정의**   | [가정] 게시물·성과·지급 내역이 흩어져 있으면 담당자가 동일 자료를 반복 대조한다.<br>[가정] 조건 미충족, 승인 여부, 지급 여부를 혼동하면 오지급·중복 지급 위험이 커진다.<br>[가정] 지급을 완료했다는 화면 표시만으로는 수령 주소와 실제 거래 결과를 확인하기 어렵다. 사용자 인터뷰로 검증한 문제는 아니다. |

### MVP 범위와 완료 기준

- 집행자 1명과 인플루언서 5명의 테스트 사용자·지갑, 활성 캠페인 1개를 대상으로 한다. 현재 제품은 PC·모바일 웹이며 네이티브 앱은 대상이 아니다.
- 피드 탐색 → 조건 검수 → 집행자의 원본 확인 → 승인 → 지급 확인 → 거래 영수증 확인을 제공한다. 반려 사유 저장과 재검수도 포함한다.
- **목업:** 프로필·게시물 사진, 캡션, 게시 시각, 좋아요·댓글·조회수. 실제 Instagram API 또는 소셜 계정 소유권 검증은 없다.
- **실제 구현:** PostgreSQL 사용자·지갑·상태 저장, 서버 서명, Maroo Testnet 체인 ID `450815`, PCL 정책, 승인 및 테스트 토큰 지급. tOKRW는 실제 원화가 아니다.
- **범위 밖:** 신규 캠페인 생성·수정 UI, 인플루언서 직접 신청·업로드·지갑 연결, 실제 Instagram 연동, 메인넷·원화 정산, 유료 과금, 운영 배포 승인.
- 완료 판정은 조건 미충족·권한 없는 요청 차단, 반려·재검수 상태 저장, 승인 예산 예약, 지급 성공 영수증과 수신 잔액 증가, 중복 지급 차단을 각각 확인하는 것이다. 이번 문서 작업에서 해당 실행 검사를 다시 수행하지 않는다.

### 2) Enum

아래 상태는 코드에서 사용하는 허용 값이다. `CampaignParticipant.status`, `ChainOperation.status`, `TestWallet.role`은 현재 Prisma enum이 아닌 문자열 필드다.

| Enum                  | 값                                                                         | 의미                                                                                   | 사용 위치                       |
| --------------------- | -------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | ------------------------------- |
| UserRole              | `Admin`, `Normal`                                                          | 집행 권한·일반 사용자                                                                  | 인증과 `/affiliate/*` 접근 제어 |
| Participant.status    | `pending`, `approving`, `approved`, `paying`, `paid`, `rejected`, `failed` | 검수 대기, 승인 거래 확인 중, 승인 완료, 지급 거래 확인 중, 지급 완료, 반려, 체인 실패 | 참여 DB·API·화면                |
| ChainOperation.status | `pending`, `confirmed`, `failed`                                           | 거래 미확정, 영수증 성공, 영수증 실패                                                  | 서명 거래 저장·복구             |

정상 전이는 `pending → approving → approved → paying → paid`다. `pending → rejected → pending`은 반려·재검수 경로다. 기록된 거래가 없을 때의 전송 준비 실패는 이전 상태로 되돌리고, 기록된 거래는 확정 전까지 진행 상태를 유지한다. 영수증 실패 시 `failed`로 표시한다. `failed` 재처리 UI는 없다. 기간 만료는 조건 계산 결과이며 별도 `expired` DB 상태는 없다.

## 6. FAQ

| 질문 (Q)                                              | 답변 (A)                                                                                                                                                      |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Q1: 실제 인스타그램을 연결하나요?**                 | 아니다. 현재 게시물·성과는 목업이다. 실제 API·계정 소유권·성과 진위 검증은 없다.                                                                              |
| **Q2: 실제 돈을 지급하나요?**                         | 실제 Maroo 테스트넷 거래로 tOKRW를 전송하지만 실제 원화나 메인넷 자산은 아니다.                                                                               |
| **Q3: 누가 승인·지급할 수 있나요?**                   | 인증된 Admin 집행자만 가능하다. 일반 인플루언서 계정에는 해당 권한이 없다.                                                                                    |
| **Q4: 승인되면 언제든 받을 수 있나요?**               | 아니다. 지급 시에도 집행기간과 조건을 검사한다. 종료 후 미지급 승인은 지급할 수 없고 잔액 회수는 컨트랙트에서 지원한다.                                       |
| **Q5: 네트워크가 끊겨 다시 누르면 중복 송금되나요?**  | 같은 operationKey의 저장된 거래를 재사용한다. 컨트랙트도 동일 수신자의 중복 지급을 차단한다. 다중 인스턴스·장애 조합에 대한 운영 보장은 추가 검증이 필요하다. |
| **Q6: 실패한 거래를 화면에서 새로 지급할 수 있나요?** | 미확정 거래 확인은 가능하지만 확정 실패 `failed` 상태의 재처리 UI는 없다. 운영 복구 절차는 미정이다.                                                          |
| **Q7: 가격과 데이터 보관 기간은 어떻게 되나요?**      | 서비스 과금은 없으며 상용 가격은 미정이다. 테스트 지갑·데이터 자동 삭제와 키 회전은 구현하지 않았고 운영 보존 기간은 결정 필요다.                             |
| **Q8: 오프라인 사용과 모바일 앱을 지원하나요?**       | 검수·정산에는 서버와 테스트넷 연결이 필요하다. 현재 대상은 반응형 웹이며 네이티브 앱은 범위 밖이다.                                                           |
| **Q9: 배포와 QA는 완료됐나요?**                       | 과거 실행 근거는 [QA 기록](QA.md)에 있다. 현재 배포 완료 여부와 마루 전환의 실거래 결과는 이 문서 작업에서 검증하지 않았다.                                   |
